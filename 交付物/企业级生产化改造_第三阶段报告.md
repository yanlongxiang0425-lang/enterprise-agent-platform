## 1. 阶段结论

第三阶段完成“数据库替换与异步执行准备”。

本阶段仍不强依赖 PostgreSQL/Redis，保持本地可运行；但代码结构已经从“本地 JSON 任务仓储”升级为“仓储协议 + 事件日志 + 文件元数据 + 执行器抽象”。后续替换为 PostgreSQL 任务表、Redis 队列或独立 worker 时，不需要推翻任务 API 和任务服务。

## 3. 当前任务事件流

```text
create-pilot-task
  -> task.status = pending
  -> event: created
  -> file_metadata: knowledge_file/template_file/result_file

run-task
  -> task.status = running
  -> event: running
  -> 调用 MaterialCompletionEngine
  -> 成功：task.status = succeeded
  -> event: succeeded
  -> metrics: rows/fields/exceptions/knowledge_rows/run_id
  -> file_metadata: 输出文件存在、size_bytes、sha256

失败场景
  -> task.status = failed
  -> event: failed
  -> error 写入任务记录
```

## 7. 当前工程等级

第三阶段后，项目已具备进一步生产化的关键中间层：

- 任务仓储不再绑定具体实现。
- 任务事件可追溯。
- 文件输入输出可审计，可用 SHA-256 做去重、复跑校验、问题定位。
- API/CLI 都能查询任务状态和事件。
- 已有 PostgreSQL 表结构草案。

仍待完成：

- 真正的 PostgreSQL 仓储实现。
- Redis/Celery/RQ 或内部队列 worker。
- 文件上传、对象存储、知识库导入。
- 鉴权、租户隔离、审计日志、脱敏。
- LangGraph checkpoint、人审节点、重试和恢复。
- OpenTelemetry、指标、集中日志。

## 8. 第四阶段建议

下一阶段建议进入“后台 worker 与任务执行解耦”：

1. 增加 `TaskExecutor` 的本地队列实现，例如 `ThreadPoolTaskExecutor`。
2. API 创建任务后返回 `task_id`，由 worker 后台执行，不阻塞 HTTP 请求。
3. 增加任务取消、重试、失败重跑。
4. 增加任务锁，避免同一个任务被重复 worker 并发执行。
5. 增加任务事件 `queued/retried/cancelled`。

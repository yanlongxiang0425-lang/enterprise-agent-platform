1. 背景与目标

1.1 现状

当前指标体系构建智能体基于 Dify Workflow 实现，部署于 aigc.midea.com/dify2，应用 ID 35b561f1-db2a-4676-8b61-2b5604731400。主链路使用 Qwen3-235B-A22B (CHAT) 模型，Agent 策略为 ReAct，工具包含 BOCHA_SEARCH（博查 Web 搜索）和领域体系构建 RAG 检索。

图 1-1 业务流程图（按用户白板还原）

1.2 痛点

  1. Dify 拖拽实现，工程化与版本管理薄弱，难以单元测试与回归
  2. 多个 Python 代码节点处理"脏活"（Unicode 转义、字符串扁平化、JSON 聚合），逻辑散落
  3. 单 Agent + 235B 巨型模型，单次 Token 成本与延迟过高
  4. 缺缓存、可观测、评测闭环
  5. 业务流程图中"重新评估/人为确认"环节尚未落地
  6. 大 JSON 输入瓶颈：上千上万张表的 schema 拼成一个 JSON，超出上下文窗口
  7. 知识库默认 pgvector，召回率与性能尚未做过严肃评估
  8. 知识库 Excel/Word 更新流程不规范，缺自动化 pipeline

1.3 改造目标

  • 从 Dify 迁出，自建可控的 Python AI 服务
  • 复用现有 PG 向量库（评估后确认满足）
  • 引入模型分流策略降本提速
  • 解决大 JSON 输入瓶颈
  • 提供离线部署能力（内网无外网）
  • 补齐审计、脱敏、可观测、人工确认

2. 总体技术路线

决策项选择关键理由
主语言Python（AI 核心）+ Java（业务接入）AI 生态首发支持；Java 团队负责接入/管理后台
Agent 编排LangGraph 1.0+状态机式编排，可调试、可重放，告别 Dify 不可控拖拽
LLM 推理引擎vLLM 0.6+（GPU）/ llama.cpp（CPU）支持 AWQ/GPTQ 量化、guided_json 结构化输出
模型策略三级分流7B 做分类/路由，32B-AWQ 做推导，Embedding/Rerank 用 BGE
向量库PostgreSQL 16 + pgvector 0.7.4知识库 < 5 万 chunk，HNSW 性能足够；同实例分 schema
模型采购路径 A：CPU 验证 → API 选型 → GPU 自部署风险最低，先验证后采购
部署单机虚拟机 + Docker Compose，全离线包内网无外网，必须自带 wheel/镜像/模型

3. 模型分流策略

图 3-1 三级模型分流策略
为什么不用 Qwen3-235B-A22B？
即使是 MoE 激活 22B，单机部署显存仍紧张（约 140GB FP8 / 200GB FP16）；单 Token 推理延迟高，QPS 100 需要多卡集群。实测 32B + RAG 已覆盖企业指标推导 90% 场景，等 GPU 采购后如果不达标再升级 72B-AWQ 即可。

4. 大 JSON 瓶颈解决方案（核心）

问题本质：上千上万张表的 schema 拼成一个 JSON，会超出模型上下文窗口，且对超长输入注意力会被稀释，业务域分类与指标推导效果都会变差。

图 4-1 大 JSON 处理 · 五层组合拳
层手段效果
L1 Schema 瘦身只保留 table / column / comment / dtype / sample单表从 ~1.5KB 压到 ~200B
L2 两阶段 Map-Reduce7B 模型按 50 张/批做分类，32B 模型按域做推导单次输入 ≤ 10KB（远小于上下文窗口）
L3 结构化输出约束vLLM guided_json + JSON Schema + Outlines 兜底杜绝模型输出"散文式" JSON
L4 流式 + SSE按业务域分块流式返回，前端渐进渲染首字时间 P95 ≤ 3s
L5 缓存 + 增量表 schema MD5 作 cache key；命中跳过 LLM重复请求 QPS 提升 10×
容量估算：10000 张表瘦身后 2MB；分类 200 批次（并行 ≤2 分钟）；推导任务按域 50 个并行（GPU 期 ≤ 15 分钟）。CPU 验证期只测功能不上量。

推荐结论：核心 AI 服务用 Python，业务接入层/管理后台保留 Java，通过 HTTP/gRPC 解耦。
  • AI 服务（Python）：指标推导、RAG 检索、业务域分类、Agent 编排
  • 业务接入层（Java）：用户管理、权限、租户、审计查询、报表导出、ERP/数仓对接
  • 解耦：Python 服务暴露 OpenAPI；Java 通过 OpenFeign/WebClient 调用

7. PG 向量库适配评估

指标当前值评估
文档总数< 1000（Excel + Word）小
字段总数顶多几万设计字段小
预估 chunk 数< 5 万小
向量维度bge-m3 = 1024标准
总向量空间5 万 × 1024 × 4B ≈ 200MB小
检索并发 QPS100中
索引类型召回率 @ 10w 向量QPS（单机 8 核）
暴力100%< 10
IVFFlat95%~200
HNSW（推荐）99%~1200
结论：pgvector HNSW 在 5 万向量规模下，单机 QPS 远超 100，满足要求且无需更换。当向量数 > 500 万 或 多租户隔离时再考虑 Milvus / Qdrant。

推荐建表 SQL

CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE kb_chunks (
  id BIGSERIAL PRIMARY KEY,
  doc_id VARCHAR(64) NOT NULL,
  domain VARCHAR(64),
  content TEXT NOT NULL,
  embedding vector(1024) NOT NULL,
  metadata JSONB,
  created_at TIMESTAMPTZ DEFAULT NOW()
);

CREATE INDEX idx_kb_chunks_embedding_hnsw
  ON kb_chunks USING hnsw (embedding vector_cosine_ops)
  WITH (m = 16, ef_construction = 64);

CREATE INDEX idx_kb_chunks_domain ON kb_chunks(domain);
CREATE INDEX idx_kb_chunks_content_fts
  ON kb_chunks USING gin(to_tsvector('jiebacfg', content));

10. docker-compose.yml 骨架

version: "3.9"

services:
  postgres:
    image: postgres:16.4-bookworm
    environment:
      POSTGRES_DB: metric_agent
      POSTGRES_USER: ma
      POSTGRES_PASSWORD: ${PG_PASSWORD}
    volumes:
      - pg_data:/var/lib/postgresql/data
      - ./init-pgvector.sql:/docker-entrypoint-initdb.d/init.sql
    ports: ["5432:5432"]

  redis:
    image: redis:7.4-bookworm
    command: redis-server --maxmemory 12gb --maxmemory-policy allkeys-lru
    volumes: [redis_data:/data]
    ports: ["6379:6379"]

  api:
    image: metric-agent-api:1.0.0
    depends_on: [postgres, redis]
    environment:
      DATABASE_URL: postgresql+asyncpg://ma:${PG_PASSWORD}@postgres:5432/metric_agent
      REDIS_URL: redis://redis:6379/0
      LLM_ROUTER_MODE: api          # 阶段 2：api / 阶段 3：vllm
    deploy: { replicas: 4 }
    ports: ["8000:8000"]

  celery-worker:
    image: metric-agent-api:1.0.0
    command: celery -A app.celery_app worker -l info -c 4
    depends_on: [postgres, redis]
    deploy: { replicas: 2 }

  vllm:
    image: vllm/vllm-openai:v0.6.3.post1
    runtime: nvidia
    profiles: ["gpu"]
    command: >
      --model /models/Qwen2.5-32B-Instruct-AWQ
      --quantization awq
      --max-model-len 32768
      --gpu-memory-utilization 0.9
      --guided-decoding-backend xgrammar
    volumes: [./models:/models]
    ports: ["8001:8000"]

  phoenix:
    image: arizephoenix/phoenix:5.10
    ports: ["6006:6006"]

  prometheus:
    image: prom/prometheus:v2.55.0
    volumes:
      - ./prometheus.yml:/etc/prometheus/prometheus.yml
      - prom_data:/prometheus
    ports: ["9090:9090"]

  grafana:
    image: grafana/grafana:11.3.0
    volumes: [grafana_data:/var/lib/grafana]
    ports: ["3000:3000"]

volumes:
  pg_data: {}
  redis_data: {}
  prom_data: {}
  grafana_data: {}

11. 选型决策一页纸 & 验收清单

关注点当前 Dify 方案新方案收益
编排Dify 拖拽LangGraph 1.0 状态机可测试、可版本化、可灰度
模型单一 Qwen3-235B7B+32B 分流成本 ↓ 60%+，延迟 ↓ 40%
大 JSON一次塞入5 层瘦身/切片/Map-Reduce/流式/缓存突破上下文窗口，准确率 ↑
向量库pgvector（沿用）pgvector + HNSW + 混合检索不换轮子，仅调优
部署Dify SaaSDocker Compose 离线包内网可控
审计/脱敏无Presidio + 三表审计合规达标
可观测弱OTel + Phoenix + Grafana分钟级定位
团队语言业务 Java + Dify 拖拽Java 接入 + Python AI（HTTP 解耦）各司其职
模型采购/路径 A：CPU 验证 → API 选型 → GPU 自部署风险最低

验收清单

  • CPU 阶段：跑通"上传 Excel → 业务域分类 → 指标推导 → 输出 metric_system JSON"全链路
  • API 阶段：5 个模型评测对比，输出选型报告
  • GPU 阶段：vLLM 部署 + 32B-AWQ + guided_json，QPS 100 下 P95 ≤ 5s
  • 知识库：5 万 chunk 入库，混合召回 Recall@10 ≥ 90%
  • 大 JSON：1000 张表稳定运行，无 OOM 与 Token 超限
  • 审计：所有 LLM 调用落审计表；PII 自动脱敏
  • 可观测：Grafana 看板 + Phoenix Trace + 告警齐全
  • 离线：依赖全打包，干净虚机一键起服
